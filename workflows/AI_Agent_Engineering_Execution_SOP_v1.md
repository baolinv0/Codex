# AI Agent 科研工程：从计划到交付的执行规范 v1.0

> 适用场景：算法研究工具链、实验分析、模型训练与评估、跨模块软件工程。来源：TMOXR Baseline Diagnosis v1 三轮复审，以及 Matt Pocock 的 `/to-spec`、`/to-tickets`、`/implement-spec`、`/code-review`、`/retro` 工作流。
>
> **目标**：一次交付尽可能覆盖原始目标；减少需要用户反复充当 Reviewer 的情况。质量责任属于主执行者，不应通过增加 Prompt 长度转移给用户。

## 一、不可变原则

1. **原始研究目标高于实现清单。** 文件、函数、测试都存在，不代表研究问题已有证据路径。
2. **计划负责定义可验收行为，Builder 负责实现并自证，Reviewer 负责找反例，主执行者负责整体验收。** Review Agent 的签字不能代替主执行者签字。
3. **先定义判据再写代码。** 对每个关键要求至少设计一个成立例、一个不成立例或禁止误判例。
4. **贯通研究证据链**：输入与监督契约 → 测量 → 错误分类 → 跨样本统计 → 候选解释 → 报告；每条重要结论必须能逆向追溯。
5. **区分三种完成状态**：代码实现完成（static/code scope）、自动化验证通过（test scope）、真实实验验收通过（evidence scope）。不得互相替代。
6. **控制复杂度**：只引入真正支持需求的接口、指标、测试和审查；不增加无关防御机制或通用 Agent 框架。

## 二、Plan：如何写可执行的 Spec

### 2.1 必须包含的六项内容

| 部分 | 应回答的问题 | 输出 |
|---|---|---|
| 研究问题与边界 | 要解决什么、明确不解决什么？ | 可判定目标、Out of Scope |
| 冻结契约 | 数据、编码域、模型、评估、版本、权限哪些不得变？ | 输入/输出与身份规则 |
| 证据链 | 哪种结论由哪些必要观测支持？ | 指标→判据→结论映射 |
| 验收矩阵 | 每个要求如何证明已实现、怎样可能被误判？ | 正例＋反例＋观察方式 |
| 任务依赖 | 哪些模块相互阻塞、接口由谁定义？ | Tickets DAG、共享 Schema |
| 最终交付 | 应产出哪些可复查文件、哪些状态必须明示？ | 文件/表格/CLI/验收报告 |

### 2.2 核心：研究验收矩阵（必填）

每个关键需求记录：`ID | 研究要求 | 必要证据与数据域 | 实现入口 | 正向例 | 反例/禁止推断 | 输出产物 | 状态与证据链接`。

TMOXR 示例：

| ID | 研究要求 | 正向验收 | 反向验收（更重要） | 输出证据 |
|---|---|---|---|---|
| TM-01 | 区分高光亮度与压缩形状 | 高光相对中间调响应不同时触发形状标签 | Prediction 全局加常数时不得仅因此认定压缩失败 | 分箱曲线、形状指标、标签证据 |
| TM-02 | 区域身份可信 | 可信 Person Mask 用于 Person 曲线 | 通用 Foreground 不得自动标记为 Person | ROI 来源、质量状态、区域曲线 |
| TM-03 | 编码域正确 | GT/Pred 统一在 2606 coded 域比较 | 没有经核验的 2606 逆变换不得声称真实线性 gain | 域说明、校准状态、gain null |
| TM-04 | 组级 Coverage 归因 | 组级稀疏率有足量支持且相对整体富集 | 200 个失败案例中只有 1 个 sparse，不得归因整组 | 分子、分母、参考率、支持/反例 |
| TM-05 | 跨模块研究闭环 | ROI GT 曲线影响 Coverage、Attribution 和 Report | 实现 ROI 曲线却从不参与最终判断，不得判完成 | 全链路追踪与样例 |

**判据可由实现者选择并解释，不要求用户预先指定所有数值阈值。** 如果某研究要求需要阈值，Builder 应提出预注册规则及适用范围，Reviewer 验证其不产生明显误判；没有足够证据则输出 `unresolved`，不凭空填结论。

### 2.3 规格粒度原则

- Spec 描述外部可观察行为和研究含义，不与文件名/实现细节过度绑定。
- Tickets 尽量是**可独立验证的纵向切片**，而不是“一个模块写完但整个链路不可用”的水平分工。
- 共享字段、颜色域、样本身份、指标公式、异常值定义必须在并行前冻结，减少接口冲突。
- 不确定研究假设用 `hypothesis + evidence required + unknown` 表述，不能包装成既定功能事实。

## 三、Build：如何执行

### 3.1 开工前

1. 读取原始 Spec、验收矩阵、仓库相关代码及现有测试；记录冻结的 base commit。
2. 将 Spec 拆为有阻塞边的 Tickets；标明每张票的可观察行为与交付证据。
3. 明确共享 Schema/接口的唯一负责人；如果多个任务修改同一共享入口，应串行或先固定接口。
4. 创建 integration branch；仅对真正独立的 Tickets 使用并行 worktree。小任务直接顺序实现。

### 3.2 每个 Ticket 的完成定义（Builder 自证）

- [ ] 实现目标行为，非 placeholder、空接口或只生成文件结构。
- [ ] 对正常路径提供最小可运行例；对研究结论提供至少一个针对误判的反例。
- [ ] 关键指标的单位、域、支持数量、missing/invalid 口径与 Spec 一致。
- [ ] 输出到下游的字段与真实消费方核对（producer → consumer），不仅验证写入成功。
- [ ] 执行可用测试；未执行、跳过和真实依赖缺失分别记录。
- [ ] 在变更清单中把本 Ticket 对应的验收矩阵行标注为 Done，并附代码/日志/产物链接。

**测试策略**：对确定性指标/算法优先使用红→绿的定向测试；跨模块需额外至少一条真实代码路径（fixture 或小型集成）验证。测试覆盖行为与结论，不追求无意义的测试数量。

### 3.3 集成阶段

- 一个 Ticket 落地后，确认其依赖者是否被解锁。
- 合并进入同一 integration branch；共享结构改动要验证全部下游调用方。
- 所有 Ticket 集成后，必须执行一次**整体验收**，而不能仅累加“每个 Ticket 都 Done”。
- 不得把旧版本的测试记录说成当前代码的验收结果。

## 四、Review：如何独立审查

### 4.1 审阅前的独立准备

Reviewer 的第一份输入是 **原始 Spec、冻结契约、验收矩阵**，而不是 Builder 的完成总结。Reviewer 必须先独立列出主要的通过条件与误判反例，再阅读代码和提交。

### 4.2 三条彼此独立的审查轴

| 审查轴 | Reviewer 必须回答 | 常见漏检 |
|---|---|---|
| **Standards** | 代码质量、可维护性、测试方式是否符合仓库规范？ | 重复、坏接口、隐式副作用 |
| **Spec & Integration** | 所有需求是否落实？接口是否从生产端一直流到消费端？是否漏掉跨模块证据？ | “模块存在但最终报告没使用” |
| **Research Semantics** | 指标能否支撑标签和结论？反例是否会误触发？单图统计可否推出组级结论？ | 高光 MAE ≠ 压缩曲线错误；one sparse ≠ group coverage |

### 4.3 必须执行的反向审查

从最终报告中抽取每一种高价值结论，反向追问：

`结论 → 触发规则 → 统计分母/支持量 → 指标公式/编码域 → 有效 ROI/样本 → 原始输入与 GT`。

遇到其中任一链接不存在、仅为默认假设、或出现反例时，提出具体问题；尽量给出可复现的最小用例。

审阅必须同时检查**所有变更相对原始 Spec**和**本轮修复相对已知问题**，两种结论单独标注。后者通过，不能自动宣告前者通过。

### 4.4 问题优先级

- **Blocker**：给出错误研究结论、错误数据域、关键路径根本未接通、原始目标无法实现。
- **Major**：核心功能/证据缺失，会影响主要实验判断。
- **Minor**：改善性能、可读性或易用性，但不影响当前研究结论。
- **Out of Scope**：非当前 Spec 所需；不强行扩展。

Reviewer 提出问题时需附：`需求ID → 代码位置 → 反例或数据场景 → 可能错误结果 → 最小修复标准`。

## 五、主执行者的最终职责（不可转交）

Reviewer 不负责交付结论，主执行者才负责。最终检查：

1. **完整性**：每条验收矩阵必须有代码证据；未完成项标注范围与原因。
2. **集成性**：跨模块研究链路经实际代码追踪，不仅看单模块测试。
3. **结论范围**：明确区分代码完成、测试完成、真实数据实验完成。
4. **审阅结果**：关键问题关闭且有对应反例；发现新问题按影响定级。
5. **交付**：提交固定 commit/PR、可运行命令、输出清单、测试实际执行状态、已知限制。

### Review/Fix 循环停止策略

1. 所有 Tickets 合并后开展**一次完整 Spec Review**（含 Standards、Integration、Research Semantics）。
2. 将问题一次性集中交给 Builder 修复，补上能复现问题的最小验证。
3. 修复后 Reviewer **定向复核问题及其相邻调用链**；主执行者重新核对整体验收矩阵。
4. 除非新增重大架构改动或暴露原审查范围外的核心功能缺失，不重新启动无边界的完整审查。
5. 可验收则交付；不可验收则明确 Blocker 与证据，而不是宣称“全部通过”。

## 六、轻量交付模板

### 6.1 Implementation Handoff（每次交付一页）

- Spec/验收矩阵版本：
- Base / HEAD / PR：
- 本次完成的需求 ID（附代码/产物定位）：
- 未完成的需求 ID（原因、影响）：
- Review：Standards / Spec / Research Semantics 分别通过或阻塞：
- 测试状态：executed pass / failed / not run / blocked（逐项）：
- 真实数据验证：executed / not run / unavailable：
- 修复记录及反例回归：
- 最终范围：**code-complete** / **verified** / **experiment-accepted**：

### 6.2 可复制的主执行者任务定义

> 你对原始研究目标的实现完整性负责，不得把独立 Reviewer 的通过直接当成最终批准。开工前将 Spec 转换为含正例、反例、代码证据、预期输出的验收矩阵。按依赖关系划分可独立验证的纵向 Tickets；共享接口先冻结，再并行。Builder 用可执行用例证明功能；Reviewer 必须先基于原 Spec 独立建立审查标准，然后按 Standards、Spec/Integration、Research Semantics 三轴审阅，反向追踪报告结论。所有模块集成后做一次完整 Spec Review；集中修复后只做定向回归与整体验收矩阵复核。不要扩展非目标功能。交付时分别说明静态代码完成、测试运行、真实实验验收的状态及证据。

## 七、如何使用 `/implement-spec`

**建议采用其可复用的编排思想，而不是为所有任务照搬整套多 Agent 流程。**

| 任务条件 | 建议做法 |
|---|---|
| 小范围修改、低耦合、少于约 2–3 个独立切片 | 单 Builder + 独立 Review；无需复杂并行 |
| 多个真实独立的实现切片、共享接口已确定 | `/to-tickets` 依赖图 + `/implement-spec` worktree 并行 + integration branch |
| 指标/模型/训练评价等高语义风险研究工具 | 在上述流程上新增 Research Semantics Review 和全链路反例 |
| 重复出现同类型失误 | `/retro` 将机械错误变成测试/静态检查，将判断性错误变成验收契约 |
